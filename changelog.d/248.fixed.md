- Regex replace-all wrote the replacement *template* into the document instead of the expanded text (#248). `replaceAll` inserted `query.replace` verbatim, so searching `(\w+)@(\w+)` in `john@a jane@b` and replacing with `$2:$1` produced `$2:$1 $2:$1` where CodeMirror 6 produces `a:john b:jane` — silent corruption of user content, not a missing feature. `SearchQuery.expandReplace` already implemented the substitution correctly and had five unit tests, and `grep -rn expandReplace --include='*.kt'` returned only its own definition and its own test file: **nothing in the product ever called it.** A green test on unreachable code is the same false comfort as an inert control, and the tests it had could not have caught this because none of them asserted anything about the *document* — they called `expandReplace` directly. The fix wires `replaceAll` (and `replaceNext`) through a new `internal SearchQuery.getReplacement(match)`, mirroring upstream `QueryType.getReplacement` — a member of a class `@codemirror/search` never exports, reachable only through the `@internal` `SearchQuery.create()`, and so absent from the 19-symbol export list of its `index.d.ts` — and the regression test asserts `view.state.doc.toString()` after the command rather than the return value of the helper. Capture groups now travel on `SearchMatch.groups` — a body property with a private setter, plus a three-argument secondary constructor, deliberately *not* a third primary-constructor component, so that the two-argument constructor and the `copy`/`copy$default` pair that ship in 0.3.5 keep their signatures; the whole `search/api/**` delta for this change is additions only, with no line removed — rather than being read off `RegExpCursor.matchGroups`, which is a *lookahead* — `advance()` runs in `init` and again after every `next()`, so `matchGroups` describes the match after the one just returned (`vim/.../VimEditor.kt:178,194` already carried comments working around exactly that). Group expansion also now follows upstream's `/\$([$&]|\d+)/g` rules it previously diverged from: `$0` and an out-of-range `$9` are left in the output verbatim rather than dropped, and multi-digit `$10` resolves to group 10 when it exists and otherwise to group 1 followed by a literal `0`. `getReplacement`'s plain-string branch is pinned by `$&` and `$$` rather than by `$1`: a plain match carries no groups, and against an empty group list the expander leaves `$1` alone anyway, so a `$1` case reads identically whether the branch is taken or not and cannot fail. `$&` and `$$` do resolve against an empty group list — to `""` and to `$` — so deleting the branch turns the test red (`expected:<[$& b $&]> but was:<[ b ]>`); both expectations are what upstream's own `StringQuery.getReplacement` returns for those queries.
- Regex replace-next silently never replaced anything, and reported success while doing it (#248). `replaceNext` decided "is the selection the current match" by string-comparing the *selected text* to `query.search` — the pattern itself. In regexp mode the pattern is essentially never equal to the text it matched, so the branch was dead: after `findNext` selected `0..6` on `john@a jane@b`, `replaceNext` returned `true` and the document was unchanged where CM6 gives `X jane@b`. Returning `true` is why nothing noticed. It now compares match *positions* against a match obtained from the query (`next.from == from && next.to == to`), as upstream does.
- `RegExpCursor` was not multiline and re-sliced the document from the end of the previous match, so `^` and `$` anchored to wherever the last match ended instead of to line boundaries (#248). Upstream's base flags are always `"gm"` — multiline is not optional — and it never re-slices. On `aa\nab\nac` the port returned `^a` → `[(0,1), (1,2)]` (CM6: `[(0,1), (3,4), (6,7)]`, and `(1,2)` is not a line start at all), `a$` → `[]` (CM6: `[(1,2)]`), and `^` → a match at *every* position 0..8 (CM6: `[(0,0), (3,3), (6,6)]`). The cursor now compiles with `RegexOption.MULTILINE` and flattens its search range once, matching from an offset into that buffer; the re-slicing was also O(n²), copying the rest of the document once per match. The buffer starts at `text.lineAt(from).from` rather than at `from`, mirroring upstream's line cursor, because the issue's reproduction starts at 0 while `findNext` searches from the **end of the current selection** — usually mid-line. Flattening from `from` would have left `^` matching at that offset, which is the same `(1,2)` defect wearing a different hat; `aMidLineSearchStartIsNotALineStart` pins it.
- Whole-word matching used XOR where upstream uses NAND, making every all-punctuation token unfindable with whole-word enabled (#248). Upstream's `stringWordTest` only requires that the characters straddling each boundary are not *both* word characters; `wordBefore != wordAfter` additionally rejected boundaries where *neither* side is a word character, so `+`, `->`, `!=`, `--` and the like could never be found. **This moved a pre-existing expectation, as #248 explicitly directed:** `SearchQueryTest.doesNotMatchNonWordsByWord` asserted **0** matches for `^_^` in `hello ^_^ world` — it codified the deviation, and its green was the reason the bug survived. It is replaced by `matchesNonWordTokensByWord`, whose expectation is CM6's own `test-query.ts` case, `test(new SearchQuery({search: "^_^", wholeWord: true}), "x[^_^]y [^_^]")` — two matches.
- `\n`, `\r`, `\t` and `\\` were never unquoted in the search or replace text (#248). Upstream computes `unquoted = unquote(search)` and searches for *that*, and runs the replace text through the same `unquote`; the port had no `unquote` at all. Searching `a\nb` in `a a\nb b` returned `[]` where CM6 returns `[(2,5)]`, so multi-line search was unreachable from the panel, and a `\n` typed into the replace field inserted a literal backslash-n. `SearchQuery.unquoted`/`unquote` now exist — `internal`, matching upstream, where both carry `/// @internal` (`src/search.ts:105,144` at `4db1811`) and neither appears in `index.d.ts` — and are used by the plain-string cursor and by both replacement paths, with `literal` disabling them as upstream specifies.
