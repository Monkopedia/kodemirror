- Published JVM and Android artifacts are now Java 11 bytecode (class-file major 55) instead of Java 21 (major 65), so consumers on JDK 11 or 17 can load them (#237). The `kodemirror.library` convention plugin declared `android { compileOptions { source/targetCompatibility = VERSION_11 } }`, but nothing anywhere in the build declared a Kotlin `jvmTarget` or a `jvmToolchain` — a repo-wide grep for `jvmToolchain|jvmTarget|JavaLanguageVersion` returned exactly one hit, in the unpublished `samples/android`. So every Kotlin JVM and Android compilation of all 57 published modules silently inherited the target of whatever JDK Gradle happened to run on, which on the release runner is the pinned JDK 21. That shipped in 0.3.4, 0.3.5 and 0.3.6, and the Android artifact contradicted the `VERSION_11` written six lines above it. Because KMP publishes no `org.gradle.jvm.version` Gradle attribute there was no resolution-time guard either: a JDK 17 consumer got a raw `UnsupportedClassVersionError` at class load, on a library whose own Compose Multiplatform dependencies are class 55 and whose coroutines dependency is class 52.
- The change is `jvm { }` and `androidTarget { }` each declaring `jvmTarget = JVM_11` plus `-Xjdk-release=11` (#237). The second half is the one `jvmTarget` alone does not give: `jvmTarget` controls the bytecode emitted, while the JDK API surface the compiler resolves against comes from the compiling JDK. #258 was exactly that gap — `removeLast()`/`removeFirst()` binding to JDK 21's `SequencedCollection`, absent below Android API 35, throwing `NoSuchMethodError` across the whole declared `minSdk = 24..34` with Kotlin diagnostics, Android Lint (#263) and desugaring all three silent. `jvmToolchain(11)` was the stated default on #237 and would cover both in one line; it was built and rejected on measurement, because it also pins the JVM that *tests* run on and `:lsp-client`'s own dependency `com.monkopedia.lsp:lsp-jvm:1.2.1` is 1450/1450 class 65, so all 11 of that module's JVM test classes die at class-load time under a JDK 11 test JVM. The pair above reaches the same published bytecode with the build and its tests still on JDK 21.
- Measured out of the artifacts rather than inferred from a green build (#237): `state`'s locally built `state-jvm-0.3.6.jar` and the `classes.jar` inside its `state-release.aar` each read **189/189 class 65 before** the change and **189/189 class 55 after**, from a wiped `state/build`. The same reader returns `{52: 973, 53: 1}` for `kotlin-stdlib:2.2.21` and `{55: 2004}` for `foundation-desktop:1.11.1`, so it distinguishes versions rather than printing a constant, and 55 in particular is a value it can emit.
- No existing consumer loses anything — a JDK 21 runtime loads class-55 bytecode — but this does change the published surface of every JVM and Android coordinate, so it is a compatibility change and not only hygiene (#237). One consumer-visible limit is unchanged by it: `:lsp-client` still needs a JDK 21 runtime, because its `com.monkopedia.lsp:lsp` dependency is class 65 regardless of what this repo emits.
