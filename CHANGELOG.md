## [Unreleased]

### Documentation
- Parameterised the docs-version grep in `CLAUDE.md`'s release step 1 so it cannot decay into a false "clean" (#293). It read `grep -rn "0\.3\.5" README.md docs-site/docs/   # previous released version`, and that literal was already false — 0.3.6 shipped on 2026-08-30 — so at the 0.3.7 cut it returns **zero hits**, which reads as *the docs are already clean* and skips the step the block exists to enforce. This is the empty-grep failure occurring inside the document written to prevent it, and it is the mechanism/disposition distinction: `com.monkopedia.kodemirror:<module>` is a fact about the artefact and stays true, while "the previous release is 0.3.5" is a fact about a queue and is false at the next cut; the two must not be baked into one command. The version is now derived from the tag list the release process itself maintains — `PREV=$(git describe --tags --abbrev=0 --match 'v*' | sed 's/^v//')` with an echoed `superseding: $PREV` control line — and the text now states that **zero hits means `$PREV` is wrong, not that the docs are clean**, the empty result being the failure mode rather than the pass condition. Verified on the branch: the command prints `superseding: 0.3.6` and finds 33 hits, matching the 33 occurrences #292 recorded bumping. `docs/release-checklist.md` step 2 takes the same form; its `# Replace 0.3.5 with the version being superseded` comment was the model for this fix but carried a literal that had gone stale the same way, so neither file now hardcodes a version.

## [0.3.6] - 2026-08-30

### Documentation
- Corrected the parity convention's modifier rule in `docs/testing-strategy.md` (#217). It read "read the modifier from the same `currentOs` the product reads", which is the tautology this release removes: a twin that asks the product which modifier is bound and then asserts that modifier is bound agrees with `platformOsName()` whatever it says. The rule now separates the two halves — derive the *press* from the keymap (still right, and why `press()` exists), but write the *expectation* down as a literal per OS name and force it with `withOs`, with what each target must call itself pinned per target by `PlatformOsNameTest`.
- Corrected the `keymap-commands` harness split in `docs/testing-strategy.md` to what #233 actually landed — **32 plain `commonTest` + 28 `runEditorTest`** — and replaced the rule that produced the wrong estimate (#201). The doc predicted only PageUp/PageDown and the vertical motions would need the Compose harness; nearly half the batch ended up there. The deciding factor is the **setup sequence, not the assertion**: `moveVertically` steps by visual row and *returns its input unchanged* when `coordsAtPos` has nothing to report, so a headless `ArrowDown` silently does nothing rather than failing, and any twin built on it passes while proving the opposite of what it claims. Many sequences reach their starting position with `ArrowDown` before anything interesting happens, so fidelity to the spec's exact sequence pulls the whole test into the Compose harness even when its final assertion is pure state. Recorded as the rule for the remaining areas, since a twin that shortcuts to the same starting offset is no longer the same test.
- Recorded why a `grep` recount of the vim suite gives 629 while 626 is correct, in `docs/testing-strategy.md` (#201). `grep -c '@Test'` over `vim/src/commonTest` counts one `@Test` inside a KDoc code sample in `VimTestHarness.kt` and two commented-out `// @Test` in `VimOperatorTest.kt`; 629 − 3 = 626, the executed count recorded in #198. Neither commented-out test carries `@Ignore`, so no runner reports them as skipped — they are invisible to every count and to CI, which is why the two bugs they document had to be filed separately as #229 and #230. Without the note a reader recounting today would take the doc for stale and "correct" 626 to 629, which is the wrong direction.
- Added `docs/testing-strategy.md`, establishing the Playwright↔`commonTest` parity convention and the obligation that keeps it from decaying (#201). The 188 behavioural `gap-analysis/` Playwright tests are **differential** — each drives the same input into real CodeMirror 6 and into KodeMirror and compares — so they cannot be migrated: the CM6 oracle does not exist inside a Compose test. (188 counts assertions only; the two capture specs are tooling, and `cm6-reference-capture` declares its `test()` inside a loop over 13 fixture files, so a static `grep` under-counts it by 12.) Both suites are kept, answering different questions ("do we still match CodeMirror 6?" on one platform, versus "does this behaviour hold on iOS/Android/wasm/native?" on six). A `parity:` comment links each twin to its counterpart in both directions, spec file and test name verbatim, so the link is greppable from either side; the doc also records why the mechanism is a process rule rather than a checked-in name table plus a failing test, and what would justify escalating to the automated check. `CLAUDE.md` carries the obligation itself, since that binds every PR: changing, renaming or deleting a parity-annotated test requires opening its counterpart in the same PR and stating which of three outcomes applies, and the reviewer must independently `grep` for the named counterparts rather than accept the author's assertion — a PR that changes one side without mentioning the other is `request_changes`, not a nit.
- Recorded the harness split for the 170 portable Playwright tests in the same doc (#201) — `188 = 170 portable + 18 Playwright-only by design`, an identity the doc states explicitly so a stale total is visible as arithmetic that stops summing: plain `commonTest` where the behaviour is a pure `EditorState` transition, and `runComposeUiTest` via `runEditorTest` where it depends on layout or on real input dispatch. For the `keymap-commands` proof batch only PageUp/PageDown and the visual-line vertical motions are layout-dependent; the arrow keys, Home/End, word motion and delete, line move/copy/delete, indent, bracket matching, transpose, the ten Shift-selection variants, select-all and undo/redo are all state transitions. Twins must derive the modifier from the same `currentOs` the product reads rather than hardcoding `Ctrl`, because `standardKeymap` carries `mac =` overrides and `platformOsName()` reports `"Mac"` on every Kotlin/Native target (#217) — the failure #200 already hit once.

Of the remaining 16, six are mode/rendering assertions that belong in Playwright permanently (block vs thin cursor, selection highlight), six are covered through a different API that key-sequence matching missed (the ex commands run via `h.doEx(...)` in `VimExCommandTest`/`VimSubstituteTest`, and `Escape`/`Ctrl-r`/`/` appear as `"<Esc>"`/`"<C-r>"`/`"/"`), and one — `ci(` — looks like a genuine hole worth one test in the existing suite, since `di(` and `ci"` are covered and change-inside-paren is not. Twins for vim would be maintenance for no coverage.

### Build
- Android Lint now analyses multiplatform source (#263). Under the legacy `com.android.library` + `androidTarget()` combination the Android variant's lint source providers were `src/main/java:src/debug/java:src/androidMain/kotlin:src/main/kotlin:src/debug/kotlin` — **`src/commonMain/kotlin` was absent**, and essentially the whole library lives there. So `lintDebug` reported "No issues found" against a nearly empty set for the life of the project, across `NewApi`, correctness, security and performance alike. That is why `NewApi` was silent about #258: all 34 `removeLast()`/`removeFirst()` call sites that throw `NoSuchMethodError` below API 35 are in `commonMain`, and lint never opened those files. The `kodemirror.library` convention plugin now walks `androidMain`'s `dependsOn` closure and registers each existing source directory on the variant's Kotlin sources via `LibraryAndroidComponentsExtension.onVariants`, so the model reads `…:src/commonMain/kotlin` for all 57 library modules (and additionally `src/jvmMain/kotlin` for `:autocomplete` and `:view`, the two modules that have one). The KMP plugin drives the Android Kotlin compilation from its own source-set model, so the addition reaches lint without duplicating sources into any compile task.
- Verified with a control that was **shown to fail first**, because "lint reports clean" is exactly the signal that was already lying (#263). Two identical deliberate `NewApi` violations were planted — one in `lezer-common/src/androidMain/kotlin` (a directory lint already listed) and one in `lezer-common/src/commonMain/kotlin`. Before the change `lintDebug` reported **2 errors, both from `androidMain`**, and said nothing about the `commonMain` file: the instrument worked and the source set was invisible. After the change the same run reports **4 errors**, the two new ones being `LintProbeCommon.kt:24` and `:26` — green to red on the file that matters. Both probes were then removed. Lint's own message on the `commonMain` hit reads *"Call requires API level 35 (current min is 24): java.util.List#removeLast (Prior to API level 35, this call would resolve to a Kotlin stdlib extension function…)"*, i.e. #258 verbatim, from the check that should have caught it three weeks before a real device did.
- A real `lintDebug` across every module on the unmodified tree is green — **0 errors, 14 warnings, 4 hints, 18 findings in all** — and **10 of the 18 are in `commonMain` files lint could not previously open** (#263): four `TextConcatSpace` warnings in generated parser tables (`:lang-cpp`, `:lang-javascript`, `:lang-php`, `:lang-rust`), two `FrequentlyChangingValue` warnings and three `AutoboxingStateCreation` hints in `:view`, and one `AutoboxingStateCreation` hint in `:lsp-client`. The remaining eight are not source findings at all: five project-level dependency-freshness warnings against `libs.versions.toml` and `gradle-wrapper.properties`, and three `:samples:android` manifest/target-SDK warnings. Counted by parsing `<issue>` elements out of all 58 `lint-results-debug.xml` reports in the CI run's own artifact rather than by adding up the per-module summary lines, which is how an earlier draft of this entry undercounted the warnings as 11 — it dropped `:samples:android`'s three from the total while still listing them. Note that the 18 findings carry **22 locations**, because `TextConcatSpace` reports two apiece; a count of `file=` attributes is therefore not a count of findings, and for this data set the location count of the `commonMain` subset (14) collides numerically with the unrelated total warning count (14). None are suppressed, baselined or fixed here.
- Wired `lintDebug` into CI as its own parallel job (#263). A check that has been fixed but is never invoked is the same inert control in a different disguise, and Android Lint was not run by any workflow: `ci.yml`'s `check` job runs `apiCheck jvmTest :view:verifyRoborazziJvm testDebugUnitTest` plus the wasm tests, and never `check` or `lint`. The new job is deliberately separate so it adds nothing to `check`'s serial time; it is **not** in `main`'s branch protection (`check`, `check-macos`, `check-ios`), so it shows on a PR without blocking a merge until a maintainer adds it.
- Recorded on #208 that migrating to `com.android.kotlin.multiplatform.library` **gates Android Lint behind the `com.android.lint` plugin rather than providing it by default** (#263). Measured against AGP 9.3.1 in a standalone probe project: with only the KMP library plugin applied, `./gradlew tasks --all` lists `androidCompileLintChecks`, `compileLint`, `bundleAndroidMainLocalLintAar` and `prepareLintJarForPublish` — all of which are about *publishing* lint checks in the AAR — and **no `lint`, `lintDebug`, `lintRelease` or report task at all**. Adding `withHostTest { }` produces exactly one analysis task, `lintAnalyzeAndroidHostTest`, with no report task to consume it, and `android.experimental.lint.analysisPerComponent=true` changes nothing. **But that is a gate, not a removal**: `KmpTaskManager` calls `LintTaskManager.createLintTasks` behind a `hasPlugin("com.android.lint")` check, and adding `id("com.android.lint")` to the same probe restores `lint`, `lintAndroidMain`, `lintFix`, `lintVital`, `updateLintBaseline` and the `generateAndroidMainLint*Model` tasks. So the migration needs to **apply `com.android.lint` and update the `lint` CI job for the new task names** (`lint` / `lintAndroidMain`, not `lintDebug`, which also means rechecking the report paths and the 58 floor) — not delete the job. An earlier draft of this entry said #208 would take lint from "runs but reads nothing" to "does not exist"; that was an inference from the absent task list and it was wrong, corrected on both #263 and #208. **Whether the restored lint actually reads `commonMain` under that plugin is unmeasured and still open.** There is reason to expect it does — `KmpComponentImpl.syncAndroidAndKmpClasspathAndSources` populates the variant's Kotlin sources from `androidKotlinCompilation.allKotlinSourceSets`, the full `dependsOn` closure — but that is an inference of exactly the kind that just failed, so #208 should run this issue's green-to-red control against the new plugin before deleting the `onVariants` block added here.
- Recorded next to `api-level: 34` in `ci-android.yml` that the level must stay **below 35** (#258). The comment justified 34 only as "between `minSdk` 24 and `compileSdk` 36" and stated that "the expected failure modes are environmental, not API-level-specific" — which #258 disproves: `SequencedCollection` arrives on Android at exactly API 35, so 34 is precisely what exposes it, and the job caught the bug on its first run. With the fix landed that emulator level stops being an arbitrary mid-range pick and becomes the regression guard for the whole `NoSuchMethodError` class. A maintainer bumping it to 35 or 36 would put `SequencedCollection` on the device and lose that detection entirely, with nothing turning red — the failure mode is silence, not a red check, which is why it has to be written down rather than inferred. A newer level should be *added* as a matrix entry, not substituted.
- Enabled klib ABI validation, so `apiCheck` now covers all six published platform coordinates instead of two (#222). `apiValidation { klib { enabled = false } }` in the `kodemirror.library` convention plugin was not merely "klib checking is off" — `klibApiCheck` was still in the task graph, still invoked by `apiCheck`, and still reported **BUILD SUCCESSFUL** while every one of its tasks (`klibApiExtractForValidation`, the four `<target>ApiBuild`s, `klibApiMerge`, `klibApiCheck`) was `SKIPPED`. So "apiCheck passes" read as "the published ABI is unchanged" and in fact meant that only for `jvm` and `android`; `wasmJs`, `macosArm64`, `iosArm64` and `iosSimulatorArm64` were unvalidated, and `git ls-tree -r main | grep -c '\.klib\.api$'` was 0 — there were no dumps to compare against. The setting now reads `enabled = true` and carries a comment recording why, which the rest of that file does for every other non-obvious setting and this one did not.
- The Apple ABI coverage this buys is **built, not inferred**, which is a stronger guarantee than "the dumps mention four targets" (#222). Kotlin/Native cross-compiles the Apple klibs from Linux, so `iosArm64ApiBuild`, `iosSimulatorArm64ApiBuild`, `macosArm64ApiBuild` and `wasmJsApiBuild` each execute for all 57 modules on the ordinary Linux `check` runner: measured 57 `klibApiMerge` and **0** `klibApiMergeInferred`, with no inference warnings. BCV's inference path — which would have reconstructed the unbuildable targets from the buildable ones — is never reached, so a symbol that exists only in `nativeMain` is caught by real compilation rather than by extrapolation. That also means the Linux job is the whole ABI gate and nothing is missing from the Apple jobs: `ci-apple.yml` runs `macosArm64Test` and `iosSimulatorArm64Test` and no `apiCheck`, and does not need one. The dumps land as one `<module>.klib.api` per module alongside the existing `api/jvm/` and `api/android/` dumps, each headed `// Targets: [iosArm64, iosSimulatorArm64, macosArm64, wasmJs]`.
- Verified with a positive control rather than by observing that the task now runs, because "runs and passes" is exactly what the inert configuration also did (#222). A `public fun` added to a `:state` commonMain file makes `:state:klibApiCheck` fail by name; reverting it makes it pass. The output is quoted in the PR.
- Added the 60 `commonTest` twins for `gap-analysis/tests/keymap-commands.spec.ts`, so every one of that spec's key sequences is now verified on jvm, android, wasmJs, macosArm64 and iosSimulatorArm64 rather than on wasm-in-a-browser alone (#201). The Playwright suite is *differential* — it drives the same input into real CodeMirror 6 and into KodeMirror and compares — and that oracle cannot exist inside a Compose test, so each twin asserts an **absolute** expectation taken from `gap-analysis/fixtures/cm6-keymap-expectations.json`, captured from real CM6. Deriving the numbers from KodeMirror's own behaviour would have made each twin a tautology that passes by construction on the platform that produced it. The twins split by what they actually depend on: 32 are plain `commonTest` (`view/src/commonTest/.../KeymapParityTest.kt`) and 28 are `runEditorTest` (`view/src/commonTest/.../input/KeymapLayoutParityTest.kt`), because `moveVertically` steps by *visual* row and returns its input unchanged when `coordsAtPos` has nothing to report — an `ArrowUp`/`ArrowDown` twin written headless would pass while proving the opposite of what it claims. Both directions of the `parity:` annotation from `docs/testing-strategy.md` are in place: each twin names its Playwright counterpart verbatim and all 60 spec tests point back at their twin. Executed-test counts read from `build/test-results/<task>/*.xml`: `:view:jvmTest` 34 + 28, `:view:wasmJsBrowserTest` 34 + 28, `:view:testDebugUnitTest` 34 (the 28 layout twins are excluded from Android local unit tests along with the rest of `view.input.*`, per #200/#215). A negative control was run on both the JVM and the headless browser — deliberately broken assertions fail on both, so the wasm run is executing rather than reporting the #197/#200 false green.
- Several twins pin a binding as doing **nothing**, which is what the capture measured rather than what the test names imply (#201). CM6's `basicSetup` carries no emacs keymap, so `Ctrl-e`/`Ctrl-b`/`Ctrl-p`/`Ctrl-n`/`Ctrl-h`/`Ctrl-k` and `Ctrl-t` leave the document and selection exactly where the preceding navigation left them — those twins are what would catch KodeMirror binding an emacs key by accident. `"Ctrl-a goes to line start"` in fact captured `anchor=0, head=229`: the emacs binding is absent and Ctrl-a falls through to select-all, so a twin written from the test's *name* would have encoded behaviour neither editor has. `Tab`/`Shift-Tab` are inert on both sides because neither setup adds `indentWithTab`. `PageUp`/`PageDown` are viewport-dependent — a page is a different number of lines in CM6's DOM and in a Compose canvas — so those two twins assert the same *direction* property the Playwright versions assert, not a frozen offset.
- The twins derive the modifier from the keymap instead of hardcoding `Ctrl` (#201). `standardKeymap` declares `KeyBinding(key = "Ctrl-Home", mac = "Meta-Home")` but `KeyBinding(key = "Ctrl-ArrowRight", mac = "Alt-ArrowRight")` — the two disagree about which modifier Mac substitutes, so even a blanket `Mod` rule would be wrong — and `platformOsName()` reports `"Mac"` on *every* Kotlin/Native target (#217), which is exactly how #200's `ctrlX_cutsSelectedText` came to pass on the JVM and fail on macOS and iOS for a reason that was not a bug. The harness therefore looks up the binding whose name on the capture platform (headless Linux) is the key the spec pressed, and presses whatever that same binding resolves to here; a key no binding claims is pressed verbatim, which is what pins it as inert. A wiring probe in the same spirit as `ClipboardCommandsTest` asserts **both** branches: the document-start modifier this platform does not bind must leave the cursor untouched, and the one it does bind must move it.
- Split a name-based `runKeyBindings` out of `handleKeyEvent` (#201). - Every `MutableList.removeLast()` / `removeFirst()` call crashed with `java.lang.NoSuchMethodError` on Android API 24-34 — the whole `minSdk = 24` range the library declares — and syntax highlighting was therefore broken on essentially every Android device in the field, in shipped 0.3.5 (#258). Compiled against a JDK 21 `java.util.List`, those two Kotlin `MutableList` extensions bind to the JDK 21 `SequencedCollection` members `List.removeLast()`/`List.removeFirst()`, which Android's `core-oj.jar` only gained in **API 35**. The measured stack was `TreeCursor.parent` -> `HighlightBuilder.highlightRange` -> `highlightTree` -> `TreeHighlighter.buildDeco` -> `KodeMirror(...)`, i.e. composing the library's headline entry point with any language extension threw on composition. All **50** call sites are rewritten to `removeAt(lastIndex)` / `removeAt(0)`, which are `List.remove(int)` — present since API 1 — and are semantically identical on every target: 34 in `commonMain` (`legacy-modes` 26, `lang-markdown` 3, `lezer-common` 3, `lang-yaml` 1, `vim` 1) and 16 in `commonTest` (15 copies of `TreeTestUtil.kt` plus `lezer-lr`'s `TestJsonParser.kt`). - Swept the sibling `SequencedCollection` APIs that would be the next instance of this and found none in `src/**` (#258): no `getFirst()`/`getLast()`, no `addFirst()`/`addLast()`, and every `reversed()` in the tree is either `IntRange.reversed()` or the `kotlin.collections` extension on a `List`, neither of which resolves to a JDK member. `first()`/`last()`/`firstOrNull()`/`lastOrNull()` are Kotlin stdlib extensions and were never at risk.
- Nothing in the build can currently see this class of bug, and that stays true after this fix (#258, and see #237). `testDebugUnitTest` is an Android *local* unit test — it runs on the host JDK 21, where `List.removeLast()` exists, so the Android runtime is never involved; `apiCheck` compares signatures and this is a runtime method-resolution failure; and the library sets no `jvmToolchain` anywhere (#237), so the compiler resolves against whatever JDK the build happens to run on and nothing fails until a device runs it. The evidence came from the Android instrumented suite added in #215/#260: **35 of 92** instrumented tests died with this `NoSuchMethodError` on the suite's first run, every one of them a test that builds a syntax tree.
- Valid code with two or more trailing comments produced spurious zero-length `⚠` nodes, wrong nesting, and — for `x = 1 /*a*/ /*b*/` — an `ArrayIndexOutOfBoundsException` out of `Tree.build` (#255). `Stack.storeNode`'s "there may be skipped nodes that have to be moved forward" branch is the port of an array idiom that has no direct Kotlin equivalent: upstream writes `this.buffer[index] = …` at `index == buffer.length` on the loop's first iteration, which grows the JS array by exactly one record, and every later iteration writes in place at a lower index. The port translated that as an unconditional `buffer.add(0)` × 4 *inside* the loop, so sinking past `N` skipped nodes left the buffer `4N` ints long instead of `4` — `4 × (N − 1)` trailing zero-filled quads that `Tree.build` reads back as real records with `term = 0` (`Term.ERR`), `start = end = 0` and `size = 0`. The same branch also declared the decremented `size` as a shadowing `var` scoped inside `if (mustMove) { … }`, so the final record was written with the undecremented parameter and claimed more children than it had. The buffer now grows once before the shift loop and the `size` shadow is hoisted out, matching `@lezer/lr`. `mustSink` is set by every reduce that ends before `stack.pos`, so this fired on any statement followed by node-producing skipped tokens — i.e. trailing comments in every grammar that has them, not an edge case.
- `platformOsName()` returned the literal `"Mac"` on *every* Kotlin/Native target, so iOS reported itself as a Mac (#217). The actual now lives per Apple family — `macosMain` answers `"Mac"`, `iosMain` answers `"iOS"` — instead of one shared `nativeMain` stub inherited from the original "add macOS and iOS native targets" commit, where all native targets were given the same implementation and nobody chose it. **No binding moved.** The mac-family test in `resolveBindingKey` was `os.contains("mac") || os.contains("darwin")`, which `"iOS"` matches neither of, so an honest name on its own would have flipped every iOS user from Cmd bindings to Ctrl bindings as a side effect; the predicate is now the named `isMacFamilyOs` and accepts the iOS family, which is what keeps iOS resolving exactly the `mac` overrides it has always resolved. The two halves are one change, not two. Whether iOS *should* diverge from macOS is a separate product question that this deliberately leaves open — it is now a one-line change on top of an honest platform name rather than one on top of a wrong one.
- Two keyboard tests could not fail on a wrong OS name, and would have confirmed this one (#217). `KeyboardHandlingTest.modX_cutsSelectedText` and the `KeymapParityHarness.isMacPlatform` helper behind `KeymapParityTest.documentStartUsesThePlatformModifier` both derived their expected modifier from `currentOs` — the same value the product resolves bindings from — so they agreed with whatever `platformOsName()` said. This is the shape that hid #171 for weeks, where `coordsAtPos` and the click hit-test both read the same `TextLayoutResult` and the round-trip could not see a divergence. Both now name the OS per case and assert the intended mapping as literals: `"Mac"`/`"iOS"` bind Meta and leave Ctrl inert, `"Linux"`/`"Windows"` the reverse, driven through the real key path with `currentOs` overridden. - Tapping a modifier key on its own — Shift, Ctrl, Alt, Meta, Caps Lock — inserted a `U+FFFF` glyph at the caret on JVM/Desktop (and Android), reported against the released 0.3.5 on macOS (#220). AWT reports `java.awt.event.KeyEvent.CHAR_UNDEFINED`, which is `U+FFFF`, for any key press that produces no character. `keyEventCharacter` and `keyEventLayoutKey` rejected code point `0` and ISO control characters, but `U+FFFF` is a Unicode *noncharacter*, not a control character, so `isISOControl()` returned false and the value fell through to text insertion. The check is now shared, lives in `commonMain` as `keyCharFromCodePoint`, and is used by both functions on JVM and on Kotlin/Native — which carried the identical hole even though a bare modifier press had not been observed to reach it. It rejects the whole class of invalid code points rather than the Shift key specifically: noncharacters (`U+FDD0`–`U+FDEF`, `U+FFFE`, `U+FFFF`), unpaired surrogates, anything outside the BMP (unrepresentable as the returned `Char`, and where Android packs its `COMBINING_ACCENT` dead-key flag), and ISO controls. `Char.isDefined()` would cover the reported case but also rejects code points merely unassigned in the platform's Unicode tables, which differ between Kotlin/JVM and Kotlin/Native, so it would drop legitimately typed characters and do so differently per target. wasmJs was unaffected: its `keyEventCharacter` always returns null and its `keyEventLayoutKey` reads the browser's `event.key`, which is `"Shift"` for a bare Shift and is discarded for being longer than one character.
- `:sort` produced different text on macOS/iOS than on JVM and Android whenever two lines compared equal (#198). Both of the ex-command's comparators answered `1` — "greater than" — for equal keys (`if (sa < sb) -1 else 1`), so `compare(a, b)` and `compare(b, a)` agreed instead of having opposite signs. That violates the comparator contract, and the order of tied lines then falls out of whichever sort algorithm the target happens to use rather than out of the comparator: JVM `Collections.sort` (TimSort) takes from the left run unless `compare(right, left) < 0`, which with the broken comparator still left ties in place, while Kotlin/Native's merge sort takes from the *right* run whenever `compare(left, right) > 0` and therefore reversed every tied group. `:sort r/in/`, where the sort key is the literal match `in` and so identical for every matching line, came out in the opposite order on the Apple targets. Both comparators now use `compareTo`, returning `0` for equal keys; `MutableList.sortWith` is contractually stable on every target (the guarantee is on the common `expect` declaration, and Kotlin/Native's merge sort honours it once the comparator is consistent), so tied lines keep their original relative order everywhere — which is what vim's `:sort` does and what the JVM output already showed. No explicit index tie-break is needed. This was a genuine cross-platform correctness bug in shipped code, invisible for as long as the `:vim` suite ran on the JVM only, and it was surfaced by moving that suite to `commonTest` in the same release: `VimExCommandTest.ex_sort_pattern_no_r` was the one failure out of 626 on both `macosArm64` and `iosSimulatorArm64` the first time the suite ran there.
- A click could occasionally teleport the caret to the start of the line instead of landing under the pointer (#171). `posFromVisibleItems` clamped the resolved character offset to the `ColumnItem`'s `[from, to)` span, but that `columnItems` snapshot can lag the `TextLayoutResult` by a frame after a content change: `BasicText` recomposes and writes its new layout (via `onTextLayout`) before the snapshot catches up, so `item.to - item.from` is momentarily stale — e.g. `0` on a just-populated line — while the layout (and thus the resolved offset) is already correct. Clamping a correct offset to that stale span collapsed every hit in that window to `item.from`, i.e. the line start. The offset is now clamped to the layout's own text length — the domain the offset was resolved against — so a hit during the stale frame lands correctly; when the snapshot is fresh the two lengths agree and behaviour is unchanged.
- The shipped `LICENSE` was not canonical Apache-2.0 (#231). Three word-level edits sat inside the operative terms — `submitted to the Licensor` and `received by the Licensor` in the §1 definitions of "Contribution" and "Contributor", and `excluding any notices` for `excluding those notices` in §4(d) — while every published POM declares `The Apache License, Version 2.0` pointing at `https://www.apache.org/licenses/LICENSE-2.0.txt` and ~800 source headers carry the standard notice, so consumers resolving from Maven Central got a licence file that differed from the URL identifying it. ## [0.3.4] - 2026-07-09

### Added
- Minimal Android sample app (`samples/android`) that embeds and builds a `KodeMirror` editor with `basicSetup` plus a Markdown language extension, unblocking the "running on Android" prerequisite (#29).
- `indentSelection` command (`:commands`): re-indents every line touched by the selection to the indentation computed by the language indent service / tree strategy (`getIndentation`), mirroring upstream `@codemirror/commands`. Skips lines where `getIndentation` returns null, applies all line changes in one transaction, and moves the cursor ahead of the indentation when it sat within the old indent. Bound in `defaultKeymap` to `Ctrl-Alt-\` (`Meta-Alt-\` on macOS) (#135).
- `CompletionConfig.asyncOverride`: suspend completion sources that the autocomplete framework launches on the editor's coroutine scope and dispatches when they resolve. This is the wasmJs-safe way to drive an async source (e.g. a language server) — the previous `asyncCompletionSource` blocking bridge throws on wasmJs (#109).
- `Completion.sortText`: an optional explicit sort key (e.g. an LSP server's `CompletionItem.sortText`) honored when ordering completions. The ranking is now score/boost descending, then `sortText` ascending when present (else label ascending) — so a server can order equal-scored items as it prefers even when their labels would sort differently. Behavior is unchanged when no option has a `sortText`. The `:lsp-client` mapping (`mapCompletionItem`) now carries `CompletionItem.sortText` through (#138).

### Fixed
- Clicks now land on the line under the pointer instead of ~a quarter-line low (#169). `posFromVisibleItems` built its line grid from `LazyListItemInfo.offset`, which starts at `y = 0`, but the `LazyColumn` renders its content shifted down by `contentTopPadding` (the content padding sits above the first item) while the pointer `offset.y` is in that padded space. The hit-test grid was therefore ~`contentTopPadding` px (~4.dp, about a quarter line) above the glyphs, so a click toward the lower part of a line resolved to the line below it. The resolver now adds `contentTopPadding` to each item top (and to the within-line `y`), aligning the hit-test with the rendered caret geometry. Measured on dpr-scaled CanvasKit the vertical offset drops from ~0.28 line to sub-pixel; centre-of-line clicks were unaffected (which is why it surfaced only as a subtle "lands slightly low" drift). Guarded by a JVM test that clicks just below a glyph's bottom edge — the band where the missing padding flipped the line.
- Clicks (and drag-select / hover) now land on the glyph under the pointer after scrolling, instead of a pre-scroll "up and to the left" position (#165). The `LineLayoutCache`'s per-line `topPx`/`leftPx` are written in `onGloballyPositioned`, which does not reliably re-fire after a scroll-without-recomposition (notably on CanvasKit/wasm), leaving them stale. Hit-testing already preferred the live `LazyListLayoutInfo` (`posFromVisibleItems`) but fell back to the stale cache (`posAtCoords`) whenever `posFromVisibleItems` returned null — and drag (`handleDrag`/`handleRectangularDrag`) and hover used the cache directly. `posFromVisibleItems` now never returns null when text lines are visible: it clamps a `y` that falls in an inter-line gap or outside the rendered range to the nearest visible line (preferring the line below, matching `LineLayoutCache.posAtCoords`). Click, drag, hover and the drop-cursor all resolve through that single live-layout resolver, so the cache is no longer consulted for absolute line position — only for within-line `x`→offset and caret drawing. The never-null line-pick is factored into `chooseHitLineIndex` and unit-tested.
- Swapping the `EditorSession` passed to `KodeMirror` no longer wedges scrolling (#166). `lazyState`/`horizontalScrollState` were not keyed on `session` while every sibling (`pluginHost`/`lineLayoutCache`/`pendingLineLayouts`/`textLayoutResults`) was, so on a session swap the previous document's scroll position/range carried over and clamped scrolling. Both scroll states are now `remember(session) { … }`.
- Vim motions now reliably reveal the cursor (#158). `gg`/`G` and offscreen `j`/`k` left the cursor off screen, and an operation could yank the viewport to the top. Vim commands run inside `cm.operation { }`, so each motion's `setCursor` transaction carried `scrollIntoView = false` (`curOp != null`); the only auto-reveal was a recovery in `onBeforeEndOperation()` gated on `op.cursorActivity`, which is set by the VimExtension plugin's `update()` → `onSelectionChange()`. That timing is unreliable for in-operation motions (and never fires in headless mode), so the reveal was often skipped — and when it did fire on an operation that hadn't moved the cursor it revealed a stale head (the "jump to top"). The operation now records the primary selection head when it begins and reveals the cursor whenever a vim operation actually *moved* the head (`isVimOp && startHead != finalHead`), independent of the `cursorActivity` flag. The no-argument `scrollIntoView()` already resolves its target to the final `selection.main.head`, so this reveals the real destination and never offset 0, while a non-moving operation no longer disturbs the viewport.
- The scroll-into-view / caret-reveal collector now survives a failing reveal request (#155). It was a single long-lived `LaunchedEffect(session) { snapshotFlow { impl.scrollRequest }.collect { … } }`; if the per-request body threw (e.g. the #152 `getCursorRect` out-of-bounds), the exception propagated out of `collect`, the effect completed exceptionally and was never relaunched (key `session` unchanged), so scroll-into-view stayed dead for the rest of the session. The per-request body is now wrapped in `try/catch`: a failure is swallowed, the request is still consumed (so a persistently-bad one isn't retried forever), and collection continues — while `CancellationException` is rethrown so effect disposal still cancels the coroutine. The same per-iteration resilience was applied to the session-scoped viewport-tracking / cache-eviction collector. Defense-in-depth on top of the #152/#154 clamp.
- Async (LSP) completion no longer re-opens the popup with a stale result. A suspend `asyncOverride` source still in flight when the user moved the cursor, changed the typed token, or closed the popup (e.g. pressed Escape) used to dispatch its result unconditionally when it resolved, re-opening the completion list and demanding an extra Escape — the symptom behind "Escape needs multiple presses to exit vim insert mode". `triggerCompletion` now captures the trigger position and, before opening the popup, re-validates the resolved result against the *live* state — mirroring the in-place re-filter in `completionStateField` (anchored `validFor.matches` over the `from`..head span, #139). A result is dropped when the selection is no longer an empty cursor, the cursor moved before the result's `from`, or the `from`..head text no longer matches `validFor` (when `validFor` is absent, only the unchanged trigger position is valid). A still-relevant result opens the popup exactly as before (#153).
- Restored the matched-prefix **bold highlighting** in the completion popup labels (#111). The label was switched from an `AnnotatedString` to a plain `String` while fixing #109 because the styled label appeared not to paint on Compose-wasmJs; that was actually an intrinsic-width-0 measurement collapse, not a paint failure. The popup already lays the label out with a bounded width + `weight(1f)`, so the `AnnotatedString` now resolves to a real width and paints on both JVM and wasmJs — the matched prefix (`FilterResult.highlighted`) renders bold again, with any `detail` folded onto the end. The popup also now renders in the editor's content font (`LocalContentTextStyle`), consistent with the gutter/panels/placeholder, which keeps the styled label deterministic for screenshot baselines.
- Editing no longer crashes (`IllegalArgumentException: offset(N) is out of bounds`) in the caret-reveal / horizontal-scroll path. The cached `TextLayoutResult` lags the document by a frame during typing and `mapTabOffset` can expand the offset, so the doc-clamped offset could exceed the layout's text length when `getCursorRect` was queried. The reveal path (`KodeMirror.kt`) and `LineLayoutCache.coordsAtPos` now clamp the offset to the **layout's** text length before querying it, not the doc line length — the same invariant the drawing-side sites already follow (#152).
- Explicit (Ctrl-Space / `startCompletion`) completion sessions now follow upstream `@codemirror/autocomplete`'s distinct lifecycle (#139). The completion state field tracks whether the active session was opened explicitly and threads that flag from the trigger into `CompletionState`. An **explicit** session may backspace back to (and including) the session's original `from` — an empty query re-shows all options and the session stays open — whereas an **implicit** (typed) session closes once the typed span is fully removed (one char past `from`), mirroring upstream's `limit = from + (explicit ? 0 : 1)` plus its backspacing guard. Backspacing before `from` always closes. Re-filtering now matches each result's `validFor` against the *whole* span text (anchored, like upstream `checkValid`), so non-spanning input (e.g. a typed space) and non-matching input close the session; and the selection resets to the top option on each refinement instead of being coerced (#139).
- Accepting a completion now applies it at every selection range whose typed prefix matches the one being completed at the primary cursor, instead of only the primary cursor. `applyCompletion`/`insertCompletionText` build the transaction with `state.changeByRange`: the primary range's replaced span (`[from, to]`) defines a prefix, and each other range gets the same relative replacement only when the document text immediately around it equals that prefix (the same token is being typed there) — non-matching ranges are left untouched. A single selection still reduces to a plain insert. Mirrors upstream `@codemirror/autocomplete` multi-cursor apply (#136).
- `moveLineUp`/`moveLineDown` now operate on every selection range, not just the primary one. Ranges are grouped into contiguous line-blocks (matching upstream `@codemirror/commands` `moveLine`): each block is swapped with the adjacent line in one transaction, all cursors/selections are remapped to follow their moved lines, edge blocks that can't move are skipped, and the command no-ops only when nothing can move (#130).
- **Lazy LSP completion now applies auto-imports via `completionItem/resolve` (#112).** Some servers (e.g. kotlin-lsp) send completion items with an empty insertion and deliver the real `textEdit`/`insertText` plus auto-import `additionalTextEdits` only on resolve. When the server advertises `completionProvider.resolveProvider` and an item still needs resolution (it carries a `data` payload, or has no concrete insertion/edits yet), accepting the completion now issues `completionItem/resolve` and applies the resolved item's insertion **and** its auto-import `additionalTextEdits` in a single transaction. Servers without resolve support, and items that are already complete, keep the previous eager behaviour. (Builds on the #109 label fallback, which kept basic insertion working but never applied the auto-imports.)
- **LSP completion now works on wasmJs (#109).** Several issues stacked: (a) the completion source was registered via `asyncCompletionSource`, whose wasmJs actual throws, so the popup never opened — `serverCompletion` now registers via the new `asyncOverride` path; (b) two `autocompletion()` extensions (e.g. `basicSetup` + `languageServerSupport`) no longer shadow each other — the `completionConfig` facet now merges completion sources across all configs instead of taking only the last; (c) the completion popup is rendered with a plain `Column` + bounded width and a `weight`-sized label so it lays out and paints on Compose-wasmJs (a `LazyColumn`/width-less `BasicText` collapsed to nothing); (d) completion labels display (and insert) correctly for servers that use lazy completion — `insertionText()` now treats an empty `textEdit.newText`/`insertText` as absent and falls back to the item label, and `mapCompletionItem` sets `displayLabel` to the item label. (Bold prefix-match highlighting was temporarily dropped on this path and is restored in #111; `completionItem/resolve` for auto-imports is tracked in #112.)
- Completion trigger characters (e.g. `.`) are no longer inserted twice on wasmJs: the hidden text field's input-echo suppression is now reset per keydown and survives the extra `onValueChange` that a completion-popup recomposition can fire (#109).
- Accepting a completion no longer crashes (`IllegalArgumentException: Invalid position …`) when the document shrank while the popup was open (e.g. backspacing before accept): `applyCompletion` now clamps the completion result's stored `from`/`to` to the current document length (#124).
- LSP completion lists now filter by the typed prefix as you type after a trigger character (e.g. typing `to` after `Cylinder(...).` narrows to `to…` instead of leaving the full member list). The server result now always carries a `validFor` prefix regex — previously it was withheld for `isIncomplete` lists, but many servers (e.g. kotlin-lsp) mark every member list incomplete, so the list never filtered and the accept range went stale (#114).
- Arrow-navigating a completion list longer than the popup now scrolls the selected row into view; the `verticalScroll` column previously did not follow the selection, so the highlight could move out of sight below the fold (#115).
- Editing no longer crashes (`IllegalArgumentException: Invalid position …`) when a coordinate query (tooltip positioning, caret reveal) holds a document position that briefly outlives a shrinking edit. `coordsAtPos`/`blockAtPos` now return null for a position outside the current document instead of throwing `lineAt` mid-render — on a delete that removes the last character a stale position is exactly `length + 1` (#127).
- Hover (and other) tooltips no longer render offscreen near the viewport edges. `TooltipLayer` now positions tooltips through a `PopupPositionProvider` that clamps the tooltip to the window and flips it above/below the anchor (respecting `strictSide`), instead of placing it at the raw caret coordinate — which landed offscreen near an edge, or for a multi-line hover range whose end sits low in the viewport (#110).
- The line caret no longer flashes to column 0 for one frame on each keystroke. The line's `TextLayoutResult` lags the document by a frame (the caret offset is transiently one past the laid-out text), and `drawLineCursor` bailed to the line-start fallback in that case (regression from #76). It now clamps the offset into the current layout, so the caret stays at the line end for the lagging frame and snaps exact the next — no visible flash (#146).
