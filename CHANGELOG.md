## [Unreleased]

### Documentation
- Added `docs/testing-strategy.md`, establishing the Playwright↔`commonTest` parity convention and the obligation that keeps it from decaying (#201). The 188 behavioural `gap-analysis/` Playwright tests are **differential** — each drives the same input into real CodeMirror 6 and into KodeMirror and compares — so they cannot be migrated: the CM6 oracle does not exist inside a Compose test. (188 counts assertions only; the two capture specs are tooling, and `cm6-reference-capture` declares its `test()` inside a loop over 13 fixture files, so a static `grep` under-counts it by 12.) Both suites are kept, answering different questions ("do we still match CodeMirror 6?" on one platform, versus "does this behaviour hold on iOS/Android/wasm/native?" on six). A `parity:` comment links each twin to its counterpart in both directions, spec file and test name verbatim, so the link is greppable from either side; the doc also records why the mechanism is a process rule rather than a checked-in name table plus a failing test, and what would justify escalating to the automated check. `CLAUDE.md` carries the obligation itself, since that binds every PR: changing, renaming or deleting a parity-annotated test requires opening its counterpart in the same PR and stating which of three outcomes applies, and the reviewer must independently `grep` for the named counterparts rather than accept the author's assertion — a PR that changes one side without mentioning the other is `request_changes`, not a nit.
- Recorded the harness split for the 170 portable Playwright tests in the same doc (#201) — `188 = 170 portable + 18 Playwright-only by design`, an identity the doc states explicitly so a stale total is visible as arithmetic that stops summing: plain `commonTest` where the behaviour is a pure `EditorState` transition, and `runComposeUiTest` via `runEditorTest` where it depends on layout or on real input dispatch. For the `keymap-commands` proof batch only PageUp/PageDown and the visual-line vertical motions are layout-dependent; the arrow keys, Home/End, word motion and delete, line move/copy/delete, indent, bracket matching, transpose, the ten Shift-selection variants, select-all and undo/redo are all state transitions. Twins must derive the modifier from the same `currentOs` the product reads rather than hardcoding `Ctrl`, because `standardKeymap` carries `mac =` overrides and `platformOsName()` reports `"Mac"` on every Kotlin/Native target (#217) — the failure #200 already hit once.
- Measured the vim overlap #201 asked for before writing any vim twin, and the answer is **do not write them** (#201). The four vim specs hold **69** tests, not the 83 the issue estimated (`vim-extended` 31, `vim-functional` 19, `vim-keyboard` 14, `vim-visual` 5). Matching each test's key sequence against the 626 vim tests moved to `commonTest` in #198 — which spell sequences as individual keys, `h.doKeys("d", "d")`, not as `"dd"` — gives **53 of 69 already covered**. Of the remaining 16, six are mode/rendering assertions that belong in Playwright permanently (block vs thin cursor, selection highlight), six are covered through a different API that key-sequence matching missed (the ex commands run via `h.doEx(...)` in `VimExCommandTest`/`VimSubstituteTest`, and `Escape`/`Ctrl-r`/`/` appear as `"<Esc>"`/`"<C-r>"`/`"/"`), and one — `ci(` — looks like a genuine hole worth one test in the existing suite, since `di(` and `ci"` are covered and change-inside-paren is not. Twins for vim would be maintenance for no coverage.
- Rewrote `docs/screenshot-compare-workflow.md` around the rigs that actually exist, and deleted the dead `captureReferenceScreenshots` Gradle task (#193). `CLAUDE.md` mandates that doc for any screenshot-comparison work, but every one of its concrete instructions was wrong: step 1 told the agent to `cd reference-screenshots`, a directory deleted in `8a27c44` (2026-03-30) when the CM6 fixtures and capture spec were folded into `gap-analysis/`; the Compose capture named `:view:recordRoborazziDesktop`, which is not a task (the real one is `recordRoborazziJvm`); and the fix loop prescribed a direct commit-and-push that `CLAUDE.md` explicitly forbids. An agent that obeyed the doc burned its run before it could look at a single pixel. The doc now points at `gap-analysis/fixtures/cm6-scenarios/` + `npm run test:cm6-ref` for the CodeMirror 6 reference side, `:view:recordRoborazziJvm` / `:view:verifyRoborazziJvm` for the Compose side, and the coderbot → `monkopedia-reviewer` PR flow for landing fixes; it also distinguishes the two rigs (Roborazzi is the committed-baseline CI gate, gap-analysis is the uncommitted reference) and documents the showcase build + Xvfb prerequisites for the wasmJs-only side-by-side specs. The root `captureReferenceScreenshots` task, whose `workingDir` was the deleted directory, is gone.
- Marked `docs/post-task-workflow.md` superseded (#193). `CLAUDE.md` already declared it obsolete, but the file itself carried no banner and still walked an agent through `git checkout main` / `git merge` / `git push` — the exact flow the repo prohibits. It now opens with a banner naming those steps as forbidden and pointing at `CLAUDE.md`; the body is retained only as a record of the older two-phase pattern.
- Fixed the non-compiling examples and the v0.1.0 coordinates in `README.md` and `docs-site/docs/**` (#192). Concretely: dropped `historyKeymap` (never existed — `history()` installs its own undo/redo bindings), `lineNumbers()` → `lineNumbers` (it is a `val`), added the missing `.extension` on the eight `javascript()` uses (a language factory returns `LanguageSupport`, not `Extension`), wrapped document offsets in `DocPos` wherever an example passed a bare `Int` to `CursorSpec`/`ChangeSpec.Single`/`EditorSelection`/`EditorSession.insertAt` etc., replaced `kotlin()` and the "GitHub Light" theme (neither has a module) with `python()` and the themes that actually ship, and corrected the one-dark import to the package that is really published (`com.monkopedia.kodemirror.themonedark`). All 32 hardcoded `0.1.0` coordinates now read `0.3.5`, and `docs/release-checklist.md` greps for the previous released version instead of `SNAPSHOT`, which by construction could never match a hardcoded coordinate. Also dropped the two Known Limitations in the README whose issues are closed as fixed (#6, #7).

### Build
- `ci-apple.yml` now uploads the JUnit XML from both Apple jobs as an artifact (#218). Those two targets run only on macOS runners and cannot be reproduced on a Linux development box, and Gradle prints a test count in its console summary only when a test fails — so a green `macosArm64Test` or `iosSimulatorArm64Test` produced no executed-test number at all, the one thing `CLAUDE.md` says never to take on trust after #197. #200 hit this directly: two `:view` tests are scoped off `macosArm64Test` because the Compose test harness cannot synthesize a wheel event there, and the exclusion had to be validated by pointing the same filter at `jvmTest` (221 → 219) rather than by reading the macOS count.
- The last macOS-only failures turned out to be the whole mouse-wheel path, and they are a limitation of the test harness rather than of the editor (#200). `HorizontalScrollTest.wheelScrollAdvancesClickOffset` and `MixedContentScrollTest.longLineScrollsAmongShortLines` are the only two tests in the tree that scroll with the wheel, and after the portable `wheelScrollRightToEnd` helper they still reported `before=26 after=26` on `macosArm64` while passing on JVM, wasmJs and `iosSimulatorArm64`. Instrumenting both axes on a macOS runner showed `horizontalScrollPx` at 0 after a positive horizontal wheel, after a negative one *and* after a vertical one, with the first-visible line index unmoved — the entire wheel path is inert there, not just the horizontal half. The cause is upstream and specific: Compose resolves a wheel delta through a per-platform `ScrollConfig`, and the macOS one (`foundation/src/macosMain/.../MacosScrollable.macos.kt`) reads the delta entirely off the underlying AppKit event — `event.appkitEventOrNull ?: return Offset.Zero`, then `hasPreciseScrollingDeltas` / `scrollingDeltaX` / `scrollingDeltaY` — so a `performMouseInput { scroll(...) }` event synthesized by the test framework, which carries no `NSEvent`, resolves to zero for *any* Compose scrollable. iOS is unaffected because `UiKitScrollConfig` folds the delta out of the Compose `PointerInputChange`s themselves and needs no native event, which is exactly why the split was macOS-only rather than native-wide. Real macOS users are unaffected: a real wheel or trackpad gesture carries an `NSEvent`. The editor contributes nothing to this — `KodeMirror` uses the stock `Modifier.horizontalScroll`, and there is no scroll-related code in any of the platform source sets. The two methods are therefore excluded from `:view:macosArm64Test` only, scoped to the methods rather than to the target or the classes, with the reasoning and the measurement recorded at the exclusion site; every other scroll test drives scrolling through semantics or a `scrollIntoView` transaction and runs on macOS unchanged.
- The Apple targets' first run of the moved suite found three failures, none of them a product bug (#200). `KeyboardHandlingTest.ctrlX_cutsSelectedText` failed on **both** macOS and iOS because `standardKeymap` declares `KeyBinding(key = "Ctrl-x", mac = "Meta-x")` and the view resolves the `mac` override off `currentOs`, which `platformOsName()` reports as `"Mac"` on every Kotlin/Native target — so Ctrl+X correctly does *not* cut there, which is the Mac convention. (CodeMirror 6 itself binds neither Ctrl-x nor Cmd-x — cut rides the native DOM `cut` event — so this is convention parity rather than a keymap that mirrors CM6 binding for binding.) The test had hard-coded Ctrl. It is now `modX_cutsSelectedText`, deriving the modifier from the same `currentOs` the product reads (the probe-the-wiring pattern #199 introduced in `ClipboardCommandsTest`) and asserting **both** branches: the modifier the platform does not bind must leave the document and the selection untouched, and the bound one must cut. That is strictly stronger than the assertion it replaces, which only ever exercised one platform's binding. `HorizontalScrollTest.wheelScrollAdvancesClickOffset` and `MixedContentScrollTest.longLineScrollsAmongShortLines` failed on macOS only, for the same reason the latter had already failed on wasm: a fixed wheel delta travels a platform-dependent number of pixels, and both tests then assert about a resulting *click offset*, so the shortfall reads like an editor bug and is not one. Both now use a `wheelScrollRightToEnd` helper that repeats the scroll until `horizontalScrollPx` stops changing, saturating the scrollable range on every target; a platform that ignored horizontal wheel events entirely would still fail, since the helper always makes at least one attempt.
- Failed tests now print their exception message in every module and on every target (#200). `tasks.withType<AbstractTestTask>` sets `exceptionFormat = FULL`; Gradle's default listener prints only `<exception class> at <file>:<line>`, which on Kotlin/Native renders as `kotlin.AssertionError at null:-1` and discards the message the test author wrote. That made the three Apple failures above undiagnosable from the CI log — they run only on macOS runners and cannot be reproduced on a Linux development box.
- Moved `:view`'s 59 Compose UI interaction tests from `jvmTest` to `commonTest`, so clicking, dragging, typing, scrolling and focus are now verified on wasmJs and the Apple targets rather than on the JVM alone (#200) — stage 3 of #196, after #198 and #199. The test bodies were already written against the multiplatform `androidx.compose.ui.test` API; the only JVM binding was `runEditorTest` in `InputTestHelper.kt`, which called `runDesktopComposeUiTest(width, height)`, plus an `org.junit.Test` import in each file. `runComposeUiTest` has no `width`/`height` parameter, and the tests click at raw pixel offsets (`click(Offset(50f, 15f))`), so the viewport is now a `Modifier.requiredSize(width.dp, height.dp)` frame with `LocalDensity` pinned to `Density(density = 1f, fontScale = 1f)`. The pin is the load-bearing half: `requiredSize` takes dp and the ambient density differs per platform (desktop ~1.0, Android/iOS device-dependent, wasm follows `devicePixelRatio`), so without it `800.dp` would be a different pixel count on every target and every existing offset would silently mean something else; at density 1 dp == px and the offsets carry over unchanged, with `fontScale = 1f` keeping text scaling out of the line heights. `kotlin.assert` is JVM-only, so the 44 assertions became `kotlin.test.assertTrue`. The 16 Roborazzi screenshot tests stay in `jvmTest` (Roborazzi is JVM/Android only), as do `RecompositionTest` and `SessionSwapScrollTest`, which drive `runDesktopComposeUiTest` plus `CountDownLatch`/`runBlocking`. Executed-test counts read from `build/test-results/<task>/*.xml`, never from BUILD SUCCESSFUL: `:view:jvmTest` **221, 0 failures** (unchanged) and `:view:wasmJsTest` **191, 0 failures**, up from 132 — the 59 moved tests, every one of them, now run in the headless browser.
- Two things had to be fixed before the wasm run meant anything (#200). First, `runComposeUiTest` returns `Unit` on the JVM but a promise on wasmJs; `runEditorTest` dropped that value, so the browser runner reported all 59 tests green in ~1ms each without executing a single assertion — the #197 failure mode in a new costume. It is caught by a negative control rather than by inspection: with deliberately broken assertions the suite still reported green, and only after `runEditorTest` and the seven block-bodied tests propagate the result do the broken assertions fail. Second, with the tests actually running, `MixedContentScrollTest.longLineScrollsAmongShortLines` failed on wasm (`before=32 after=110`, needing +100). The wheel-delta-to-pixel factor is platform-specific — a 600-unit horizontal scroll moves ~3200px on desktop but ~550px in a browser — while the editor scrolled correctly on both. The scroll now uses a delta larger than the line's scrollable range so it saturates everywhere, which is what #67 is about; the assertion is untouched.
- Left the moved tests out of `:view:testDebugUnitTest`, with the reasoning in `view/build.gradle.kts` and the follow-up in #215 (#200). They still compile for Android, so an Android-only compile break is still caught. Android's `runComposeUiTest` launches a real `ComponentActivity` through `ActivityScenario` and therefore needs an Android framework; a plain local unit-test JVM has none and dies on a null `android.os.Build.FINGERPRINT`. Robolectric was tried and does host them — all 191 execute with `ui-test-manifest` on `debugImplementation`, `unitTests.isIncludeAndroidResources`, a `w1000dp-h800dp-mdpi` qualifier so the simulated screen is at least as large as the test frame, and an `expect`/`actual` base class carrying the Android-only `@RunWith(RobolectricTestRunner::class)` — but neither graphics mode gives a trustworthy answer. Under the default `graphicsMode=LEGACY` all text measures to zero width (a click 30px into `Hello world` resolves to offset 11, and a drag from x=20 to x=200 within one line selects nothing), which makes every coordinate assertion meaningless; under `graphicsMode=NATIVE` the metrics are right but a pointer *press* clears Compose focus (`hasFocus` true after composition, false immediately after `press()`), breaking the focus and keyboard suites. Graphics mode cannot plausibly change focus semantics, so that is an artifact of the environment, not a finding about the editor — and suppressing whichever half fails would have been exactly the wrong move. Real Android coverage needs instrumented tests on a device or emulator.

- Left nine of `:lsp-client`'s twelve test files in `jvmTest` (#199), 129 of the module's 166 test methods. The issue assumed all 35 files "move as-is"; these nine do not. Every `LanguageServer` stub in the module is a `java.lang.reflect.Proxy` — the shared `TestLanguageServer` fixture plus four per-file inline stubs — because `LanguageServer` is a ~78-method interface with no default implementations, so the JVM's dynamic proxy is what makes a one-method-scripted fake practical. Four of the files also drive suspend calls with `kotlinx.coroutines.runBlocking`, which does not exist on wasmJs/JS, and `kotlinx-coroutines-test` is not currently a dependency anywhere in the tree. Porting them needs a hand-written common `LanguageServer` implementation (or a codegen'd one), a per-method default for the ~10 methods with non-nullable return types, a new `runTest` dependency, and a rewrite of five stub factories — a change of a different shape and size from a file move, so it is deliberately not bundled here. The three files that carry no such coupling (`DocumentSyncTest`, `ServerDiagnosticsTest`, `ServerHoverTest`) did move.
- `:view`'s `ClipboardCommandsTest` was the one file in the batch carrying an `org.junit` import; it is converted to `kotlin.test.Test` rather than left behind, since that single import was all it used JUnit for (#199). Moving it to `commonTest` did expose a real platform divergence: two assertions hard-coded the JVM's behaviour of `writeClipboard()`, which falls back to Compose's `ClipboardManager` only when `platformWriteClipboard()` declines the write. On wasmJs that `actual` writes `navigator.clipboard` itself and returns `true`, so the Compose fallback is deliberately skipped and `ClipboardManager` stays untouched — `assertEquals("Hello", cm.stored?.text)` failed on the headless-browser runner. This is intended behaviour (the browser write has to happen synchronously inside the originating key gesture), not a bug, so the test now probes `platformWriteClipboard` to derive which path to expect and asserts the negative case too — strictly stronger than the assertion it replaces. `RecompositionTest` and `SessionSwapScrollTest`, listed as non-Compose candidates, both drive `runDesktopComposeUiTest` and stay in `jvmTest` for #200.

- Bumped the Android Gradle Plugin 8.13.2 → **9.3.1** (#195), a major-version migration that reaches all ~60 modules at once through the `kodemirror.library` convention plugin. 8.13.2 is the last AGP 8.x release, so there was no patch path. AGP 9 requires Gradle 9.5.0+ and JDK 17+, both already satisfied; `compileSdk = 36` / `minSdk = 24` / build-tools 36.0.0 are unchanged and within AGP 9.3's supported range. Two AGP 9 default flips break the Kotlin Multiplatform `androidTarget()` + `com.android.library` combination this repo uses, and both are opted back out of in `gradle.properties`: `android.newDsl` (AGP 9's new Android DSL — the KMP plugin fails at apply time with `LibraryExtensionImpl$AgpDecorated_Decorated cannot be cast to com.android.build.gradle.BaseExtension`) and `android.builtInKotlin` (AGP now registers its own `kotlin` extension, colliding with KMP's: "Cannot add extension with name 'kotlin'"). Both flags had to be written in the `systemProp.org.gradle.project.` form: `kodemirror.library` is a precompiled script plugin in the `convention-plugins` included build, and Gradle generates its type-safe accessors by applying the plugin block to a synthetic project that reads neither the root nor the included build's `gradle.properties`, so a plain project property — and even `-Pandroid.newDsl=false` on the command line — never reaches `generatePrecompiledScriptPluginAccessors` and the build dies before a single module is configured. AGP marks both opt-outs deprecated and removes the legacy APIs behind them in AGP 10, so the real migration to the `com.android.kotlin.multiplatform.library` plugin (source-set renames, opt-in host tests, opt-in Java compilation) is tracked separately in #208. The bump is ABI-neutral: `apiCheck` passes with no `.api` diff.

- Moved wasmJs tests onto a headless-browser runner and turned them on for 22 more modules (#202). `kodemirror.library` configured `wasmJs { nodejs() }`, and under Node any test binary that reaches Compose fails: with the skiko runtime absent webpack/Node reports `Cannot find module '.../skiko.mjs'`, and once it *is* present (the modules that apply the Compose plugin) emscripten aborts with `both async and sync fetching of the wasm failed` — skiko publishes a browser-only build of `skiko.mjs`, so no amount of asset placement makes Node work. Both failures were re-confirmed on the current toolchain (Kotlin 2.4.10, Compose MP 1.11.1, AGP 9.3.1, Gradle 9.6.1). Pixel/screenshot assertions remain off-limits on this runner: headless CanvasKit renders a fallback font rather than the bundled Compose-Resources one (#210).

### Fixed
- Tapping a modifier key on its own — Shift, Ctrl, Alt, Meta, Caps Lock — inserted a `U+FFFF` glyph at the caret on JVM/Desktop (and Android), reported against the released 0.3.5 on macOS (#220). AWT reports `java.awt.event.KeyEvent.CHAR_UNDEFINED`, which is `U+FFFF`, for any key press that produces no character. `keyEventCharacter` and `keyEventLayoutKey` rejected code point `0` and ISO control characters, but `U+FFFF` is a Unicode *noncharacter*, not a control character, so `isISOControl()` returned false and the value fell through to text insertion. The check is now shared, lives in `commonMain` as `keyCharFromCodePoint`, and is used by both functions on JVM and on Kotlin/Native — which carried the identical hole even though a bare modifier press had not been observed to reach it. It rejects the whole class of invalid code points rather than the Shift key specifically: noncharacters (`U+FDD0`–`U+FDEF`, `U+FFFE`, `U+FFFF`), unpaired surrogates, anything outside the BMP (unrepresentable as the returned `Char`, and where Android packs its `COMBINING_ACCENT` dead-key flag), and ISO controls. `Char.isDefined()` would cover the reported case but also rejects code points merely unassigned in the platform's Unicode tables, which differ between Kotlin/JVM and Kotlin/Native, so it would drop legitimately typed characters and do so differently per target. wasmJs was unaffected: its `keyEventCharacter` always returns null and its `keyEventLayoutKey` reads the browser's `event.key`, which is `"Shift"` for a bare Shift and is discarded for being longer than one character.
- `:sort` produced different text on macOS/iOS than on JVM and Android whenever two lines compared equal (#198). Both of the ex-command's comparators answered `1` — "greater than" — for equal keys (`if (sa < sb) -1 else 1`), so `compare(a, b)` and `compare(b, a)` agreed instead of having opposite signs. That violates the comparator contract, and the order of tied lines then falls out of whichever sort algorithm the target happens to use rather than out of the comparator: JVM `Collections.sort` (TimSort) takes from the left run unless `compare(right, left) < 0`, which with the broken comparator still left ties in place, while Kotlin/Native's merge sort takes from the *right* run whenever `compare(left, right) > 0` and therefore reversed every tied group. `:sort r/in/`, where the sort key is the literal match `in` and so identical for every matching line, came out in the opposite order on the Apple targets. Both comparators now use `compareTo`, returning `0` for equal keys; `MutableList.sortWith` is contractually stable on every target (the guarantee is on the common `expect` declaration, and Kotlin/Native's merge sort honours it once the comparator is consistent), so tied lines keep their original relative order everywhere — which is what vim's `:sort` does and what the JVM output already showed. No explicit index tie-break is needed. This was a genuine cross-platform correctness bug in shipped code, invisible for as long as the `:vim` suite ran on the JVM only, and it was surfaced by moving that suite to `commonTest` in the same release: `VimExCommandTest.ex_sort_pattern_no_r` was the one failure out of 626 on both `macosArm64` and `iosSimulatorArm64` the first time the suite ran there.
- A click could occasionally teleport the caret to the start of the line instead of landing under the pointer (#171). `posFromVisibleItems` clamped the resolved character offset to the `ColumnItem`'s `[from, to)` span, but that `columnItems` snapshot can lag the `TextLayoutResult` by a frame after a content change: `BasicText` recomposes and writes its new layout (via `onTextLayout`) before the snapshot catches up, so `item.to - item.from` is momentarily stale — e.g. `0` on a just-populated line — while the layout (and thus the resolved offset) is already correct. Clamping a correct offset to that stale span collapsed every hit in that window to `item.from`, i.e. the line start. The offset is now clamped to the layout's own text length — the domain the offset was resolved against — so a hit during the stale frame lands correctly; when the snapshot is fresh the two lengths agree and behaviour is unchanged.

Behaviour is unchanged — nothing is removed and both functions work exactly as before; the `@Suppress("DEPRECATION")` stays, because Kotlin still reports the deprecation for a deprecated caller of a deprecated callee. ## [0.3.4] - 2026-07-09

### Added
- Minimal Android sample app (`samples/android`) that embeds and builds a `KodeMirror` editor with `basicSetup` plus a Markdown language extension, unblocking the "running on Android" prerequisite (#29).
- `indentSelection` command (`:commands`): re-indents every line touched by the selection to the indentation computed by the language indent service / tree strategy (`getIndentation`), mirroring upstream `@codemirror/commands`. Skips lines where `getIndentation` returns null, applies all line changes in one transaction, and moves the cursor ahead of the indentation when it sat within the old indent. Bound in `defaultKeymap` to `Ctrl-Alt-\` (`Meta-Alt-\` on macOS) (#135).
- `CompletionConfig.asyncOverride`: suspend completion sources that the autocomplete framework launches on the editor's coroutine scope and dispatches when they resolve. This is the wasmJs-safe way to drive an async source (e.g. a language server) — the previous `asyncCompletionSource` blocking bridge throws on wasmJs (#109).
- `Completion.sortText`: an optional explicit sort key (e.g. an LSP server's `CompletionItem.sortText`) honored when ordering completions. The ranking is now score/boost descending, then `sortText` ascending when present (else label ascending) — so a server can order equal-scored items as it prefers even when their labels would sort differently. Behavior is unchanged when no option has a `sortText`. The `:lsp-client` mapping (`mapCompletionItem`) now carries `CompletionItem.sortText` through (#138).

### Fixed
- Clicks now land on the line under the pointer instead of ~a quarter-line low (#169). `posFromVisibleItems` built its line grid from `LazyListItemInfo.offset`, which starts at `y = 0`, but the `LazyColumn` renders its content shifted down by `contentTopPadding` (the content padding sits above the first item) while the pointer `offset.y` is in that padded space. The hit-test grid was therefore ~`contentTopPadding` px (~4.dp, about a quarter line) above the glyphs, so a click toward the lower part of a line resolved to the line below it. The resolver now adds `contentTopPadding` to each item top (and to the within-line `y`), aligning the hit-test with the rendered caret geometry. Measured on dpr-scaled CanvasKit the vertical offset drops from ~0.28 line to sub-pixel; centre-of-line clicks were unaffected (which is why it surfaced only as a subtle "lands slightly low" drift). Guarded by a JVM test that clicks just below a glyph's bottom edge — the band where the missing padding flipped the line.
- Clicks (and drag-select / hover) now land on the glyph under the pointer after scrolling, instead of a pre-scroll "up and to the left" position (#165). The `LineLayoutCache`'s per-line `topPx`/`leftPx` are written in `onGloballyPositioned`, which does not reliably re-fire after a scroll-without-recomposition (notably on CanvasKit/wasm), leaving them stale. Hit-testing already preferred the live `LazyListLayoutInfo` (`posFromVisibleItems`) but fell back to the stale cache (`posAtCoords`) whenever `posFromVisibleItems` returned null — and drag (`handleDrag`/`handleRectangularDrag`) and hover used the cache directly. `posFromVisibleItems` now never returns null when text lines are visible: it clamps a `y` that falls in an inter-line gap or outside the rendered range to the nearest visible line (preferring the line below, matching `LineLayoutCache.posAtCoords`). Click, drag, hover and the drop-cursor all resolve through that single live-layout resolver, so the cache is no longer consulted for absolute line position — only for within-line `x`→offset and caret drawing. The never-null line-pick is factored into `chooseHitLineIndex` and unit-tested.
- Swapping the `EditorSession` passed to `KodeMirror` no longer wedges scrolling (#166). `lazyState`/`horizontalScrollState` were not keyed on `session` while every sibling (`pluginHost`/`lineLayoutCache`/`pendingLineLayouts`/`textLayoutResults`) was, so on a session swap the previous document's scroll position/range carried over and clamped scrolling. Both scroll states are now `remember(session) { … }`.
- Vim motions now reliably reveal the cursor (#158). `gg`/`G` and offscreen `j`/`k` left the cursor off screen, and an operation could yank the viewport to the top. Vim commands run inside `cm.operation { }`, so each motion's `setCursor` transaction carried `scrollIntoView = false` (`curOp != null`); the only auto-reveal was a recovery in `onBeforeEndOperation()` gated on `op.cursorActivity`, which is set by the VimExtension plugin's `update()` → `onSelectionChange()`. That timing is unreliable for in-operation motions (and never fires in headless mode), so the reveal was often skipped — and when it did fire on an operation that hadn't moved the cursor it revealed a stale head (the "jump to top"). The operation now records the primary selection head when it begins and reveals the cursor whenever a vim operation actually *moved* the head (`isVimOp && startHead != finalHead`), independent of the `cursorActivity` flag. The no-argument `scrollIntoView()` already resolves its target to the final `selection.main.head`, so this reveals the real destination and never offset 0, while a non-moving operation no longer disturbs the viewport.
- The scroll-into-view / caret-reveal collector now survives a failing reveal request (#155). It was a single long-lived `LaunchedEffect(session) { snapshotFlow { impl.scrollRequest }.collect { … } }`; if the per-request body threw (e.g. the #152 `getCursorRect` out-of-bounds), the exception propagated out of `collect`, the effect completed exceptionally and was never relaunched (key `session` unchanged), so scroll-into-view stayed dead for the rest of the session. The per-request body is now wrapped in `try/catch`: a failure is swallowed, the request is still consumed (so a persistently-bad one isn't retried forever), and collection continues — while `CancellationException` is rethrown so effect disposal still cancels the coroutine. The same per-iteration resilience was applied to the session-scoped viewport-tracking / cache-eviction collector. Defense-in-depth on top of the #152/#154 clamp.
- Async (LSP) completion no longer re-opens the popup with a stale result. A suspend `asyncOverride` source still in flight when the user moved the cursor, changed the typed token, or closed the popup (e.g. pressed Escape) used to dispatch its result unconditionally when it resolved, re-opening the completion list and demanding an extra Escape — the symptom behind "Escape needs multiple presses to exit vim insert mode". `triggerCompletion` now captures the trigger position and, before opening the popup, re-validates the resolved result against the *live* state — mirroring the in-place re-filter in `completionStateField` (anchored `validFor.matches` over the `from`..head span, #139). A result is dropped when the selection is no longer an empty cursor, the cursor moved before the result's `from`, or the `from`..head text no longer matches `validFor` (when `validFor` is absent, only the unchanged trigger position is valid). A still-relevant result opens the popup exactly as before (#153).
- Restored the matched-prefix **bold highlighting** in the completion popup labels (#111). The label was switched from an `AnnotatedString` to a plain `String` while fixing #109 because the styled label appeared not to paint on Compose-wasmJs; that was actually an intrinsic-width-0 measurement collapse, not a paint failure. The popup already lays the label out with a bounded width + `weight(1f)`, so the `AnnotatedString` now resolves to a real width and paints on both JVM and wasmJs — the matched prefix (`FilterResult.highlighted`) renders bold again, with any `detail` folded onto the end. The popup also now renders in the editor's content font (`LocalContentTextStyle`), consistent with the gutter/panels/placeholder, which keeps the styled label deterministic for screenshot baselines.
- Editing no longer crashes (`IllegalArgumentException: offset(N) is out of bounds`) in the caret-reveal / horizontal-scroll path. The cached `TextLayoutResult` lags the document by a frame during typing and `mapTabOffset` can expand the offset, so the doc-clamped offset could exceed the layout's text length when `getCursorRect` was queried. The reveal path (`KodeMirror.kt`) and `LineLayoutCache.coordsAtPos` now clamp the offset to the **layout's** text length before querying it, not the doc line length — the same invariant the drawing-side sites already follow (#152).
- Explicit (Ctrl-Space / `startCompletion`) completion sessions now follow upstream `@codemirror/autocomplete`'s distinct lifecycle (#139). The completion state field tracks whether the active session was opened explicitly and threads that flag from the trigger into `CompletionState`. An **explicit** session may backspace back to (and including) the session's original `from` — an empty query re-shows all options and the session stays open — whereas an **implicit** (typed) session closes once the typed span is fully removed (one char past `from`), mirroring upstream's `limit = from + (explicit ? 0 : 1)` plus its backspacing guard. Backspacing before `from` always closes. Re-filtering now matches each result's `validFor` against the *whole* span text (anchored, like upstream `checkValid`), so non-spanning input (e.g. a typed space) and non-matching input close the session; and the selection resets to the top option on each refinement instead of being coerced (#139).
- Accepting a completion now applies it at every selection range whose typed prefix matches the one being completed at the primary cursor, instead of only the primary cursor. `applyCompletion`/`insertCompletionText` build the transaction with `state.changeByRange`: the primary range's replaced span (`[from, to]`) defines a prefix, and each other range gets the same relative replacement only when the document text immediately around it equals that prefix (the same token is being typed there) — non-matching ranges are left untouched. A single selection still reduces to a plain insert. Mirrors upstream `@codemirror/autocomplete` multi-cursor apply (#136).
- `moveLineUp`/`moveLineDown` now operate on every selection range, not just the primary one. Ranges are grouped into contiguous line-blocks (matching upstream `@codemirror/commands` `moveLine`): each block is swapped with the adjacent line in one transaction, all cursors/selections are remapped to follow their moved lines, edge blocks that can't move are skipped, and the command no-ops only when nothing can move (#130).
- **Lazy LSP completion now applies auto-imports via `completionItem/resolve` (#112).** Some servers (e.g. kotlin-lsp) send completion items with an empty insertion and deliver the real `textEdit`/`insertText` plus auto-import `additionalTextEdits` only on resolve. When the server advertises `completionProvider.resolveProvider` and an item still needs resolution (it carries a `data` payload, or has no concrete insertion/edits yet), accepting the completion now issues `completionItem/resolve` and applies the resolved item's insertion **and** its auto-import `additionalTextEdits` in a single transaction. Servers without resolve support, and items that are already complete, keep the previous eager behaviour. (Builds on the #109 label fallback, which kept basic insertion working but never applied the auto-imports.)
- **LSP completion now works on wasmJs (#109).** Several issues stacked: (a) the completion source was registered via `asyncCompletionSource`, whose wasmJs actual throws, so the popup never opened — `serverCompletion` now registers via the new `asyncOverride` path; (b) two `autocompletion()` extensions (e.g. `basicSetup` + `languageServerSupport`) no longer shadow each other — the `completionConfig` facet now merges completion sources across all configs instead of taking only the last; (c) the completion popup is rendered with a plain `Column` + bounded width and a `weight`-sized label so it lays out and paints on Compose-wasmJs (a `LazyColumn`/width-less `BasicText` collapsed to nothing); (d) completion labels display (and insert) correctly for servers that use lazy completion — `insertionText()` now treats an empty `textEdit.newText`/`insertText` as absent and falls back to the item label, and `mapCompletionItem` sets `displayLabel` to the item label. (Bold prefix-match highlighting was temporarily dropped on this path and is restored in #111; `completionItem/resolve` for auto-imports is tracked in #112.)
- Completion trigger characters (e.g. `.`) are no longer inserted twice on wasmJs: the hidden text field's input-echo suppression is now reset per keydown and survives the extra `onValueChange` that a completion-popup recomposition can fire (#109).
- Accepting a completion no longer crashes (`IllegalArgumentException: Invalid position …`) when the document shrank while the popup was open (e.g. backspacing before accept): `applyCompletion` now clamps the completion result's stored `from`/`to` to the current document length (#124).
- LSP completion lists now filter by the typed prefix as you type after a trigger character (e.g. typing `to` after `Cylinder(...).` narrows to `to…` instead of leaving the full member list). The server result now always carries a `validFor` prefix regex — previously it was withheld for `isIncomplete` lists, but many servers (e.g. kotlin-lsp) mark every member list incomplete, so the list never filtered and the accept range went stale (#114).
- Arrow-navigating a completion list longer than the popup now scrolls the selected row into view; the `verticalScroll` column previously did not follow the selection, so the highlight could move out of sight below the fold (#115).
- Editing no longer crashes (`IllegalArgumentException: Invalid position …`) when a coordinate query (tooltip positioning, caret reveal) holds a document position that briefly outlives a shrinking edit. `coordsAtPos`/`blockAtPos` now return null for a position outside the current document instead of throwing `lineAt` mid-render — on a delete that removes the last character a stale position is exactly `length + 1` (#127).
- Hover (and other) tooltips no longer render offscreen near the viewport edges. `TooltipLayer` now positions tooltips through a `PopupPositionProvider` that clamps the tooltip to the window and flips it above/below the anchor (respecting `strictSide`), instead of placing it at the raw caret coordinate — which landed offscreen near an edge, or for a multi-line hover range whose end sits low in the viewport (#110).
- The line caret no longer flashes to column 0 for one frame on each keystroke. The line's `TextLayoutResult` lags the document by a frame (the caret offset is transiently one past the laid-out text), and `drawLineCursor` bailed to the line-start fallback in that case (regression from #76). It now clamps the offset into the current layout, so the caret stays at the line end for the lagging frame and snaps exact the next — no visible flash (#146).

### Fixed
- Goal/sticky-column ("column memory") is preserved across vertical cursor moves again (regressed by the visual-row motion change) (#87)
- Vim gj/gk now move by visual (wrapped) row (#77)
- Caret height and gutter alignment on wrapped lines (#75)
- `KodeMirror` placed under an unbounded vertical constraint (a parent with `Modifier.verticalScroll(...)`, `wrapContentHeight()`, or another scrolling container) no longer collapses to zero height or crashes the inner `LazyColumn` (which disallows an infinite `maxHeight`). The editor now grows to its content height so the surrounding scroll container can scroll it. The `KodeMirror` KDoc documents the height contract: callers should give the editor a bounded height for in-editor scrolling and caret reveal (#33)
- Cursor now scrolls horizontally into view in no-wrap mode (#69)
- Horizontal scroll/scrollbar now works for documents with mixed line lengths (#67)
- Clicking on a long line clipped the cursor toward the end of the line (you could not click past a certain column and had to use the keyboard). Lines were soft-wrapped but pinned to a single visual-row height, so only the first visible region resolved to an offset. Matching CodeMirror 6, the editor now does NOT wrap by default — long lines lay out at full width and the content scrolls horizontally, so clicks resolve to the correct offset across the whole line. The `lineWrapping` extension (previously a dead CSS attribute) now actually enables soft wrapping (#20)
- wasmJs editor no longer swallows browser-reserved keyboard shortcuts (Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+PgUp/PgDn, Ctrl+1–9, Ctrl+W/T/L, …) — the document keydown listener now calls `preventDefault()` only when the editor's keymap actually handled the key, so unbound modified/special keys propagate to the browser (#49)
- Copy/cut/paste did not reach the system clipboard on the Compose/wasm target (vim `y`, emacs, and default keymaps) — the canvas render has no DOM `contenteditable`, so the copy/cut commands now bridge to `navigator.clipboard.writeText` synchronously within the originating key gesture (with a hidden-textarea `execCommand` fallback) and paste primes its buffer from `navigator.clipboard.readText`; the in-editor buffer from #16 remains the immediate fallback. JVM/desktop continues to use Compose's `ClipboardManager` (#34)
- Transactions with `scrollIntoView` now actually scroll the view: the editor was never reacting to the flag, so selection jumps that landed off-screen (vim `n`/`N` search-repeat, goto-line, history/undo, etc.) left the target invisible. The line list now scrolls the primary selection head into view, matching CodeMirror 6's `scrollIntoView` "nearest" behavior (#58, #33)
- Vim dot-repeat (`.`) dropped the inserted text of change/insert commands (`c`, `cw`, `s`, `i`, `a`, `o`, …) — the insert-mode change event was never wired up, so `lastInsertModeChanges` stayed empty and `.` replayed only the operator/delete (#21)
- Vim change/insert commands (`c`, `cw`, `s`, …) were not a single undo unit — `u` took two steps to revert because the insert-entry cursor selection stamped a history boundary on the operator-delete event (#23)
- Active-line and line-decoration highlight backgrounds again fill the full editor width in no-wrap mode (regressed by the horizontal-scroll layout work) (#85)
